# 개발 규칙 준수
수정/개선/보완 작업 진행 후 문제 발생 원인도 알려줘.
문제 개선 시 살을 덧붙이는 방법은 지양하고 항상 근본적인 원인 해결.
항상 한글로 존댓말 사용.
한글이 있는 파일은 UTF8 인코딩 유지.
절대 추론해서 답변하지 마라. 추론할 경우 (추론) 이라고 표시해라.

## 작업 후 즉시 커밋·푸시·배포 실행 절차(Assistant 실행 체크리스트)
- 목적: “작은 수정이라도 매번 버전업/커밋/푸시/배포”를 Assistant가 스스로 보장한다.
- 적용 범위: 코드/CSS/HTML/문서/규칙 등 모든 변경. 대화 상 별도 확인 없이 자동 수행한다.
- 사용자님은 이 프로젝트의 개발 작업에 대한 커밋·푸시·운영 배포를 상시 승인하셨다. 별도 언급이 없어도 진행하며, 관련 테스트·버전·캐시 갱신·생성 빌드 산출물과 현재 보류 중인 변경도 포함한다. 파일 수 증가를 이유로 사용자님께 재승인을 요청하지 않는다.
- 예외: 사용자가 명시적으로 “커밋/푸시/배포 하지 말라”고 지시한 경우에만 해당 작업을 생략한다.
- 자동화가 비활성화된 환경에서도 Assistant는 명령을 직접 실행해 본 절차를 보장한다.

### 표준 실행 순서(항상 동일)
1) 테스트 실행  
   - 명령: `npm test`  
   - 테스트가 정의되어 있지 않으면 건너뛴다. 테스트가 실패하면 커밋을 보류하고 원인을 보고한다.
2) 버전 증가  
   - 파일: `prototype/js/config.js`의 `config.APP_VERSION`  
   - 규칙: 패치 레벨 +1. 변경이 없다면 자동으로 증가시킨 뒤 스테이징한다.
3) 스테이징  
   - 명령: `git add -A`
4) 커밋  
   - 명령: `git commit -m "<한국어 요약> · 앱 버전 X.YYY"`  
   - 메시지에 변경 요지와 버전을 반드시 포함한다.
5) 푸시  
   - 명령: `git push origin main`
6) 운영 배포 및 확인
   - 기존 배포 경로는 GitHub `main` 푸시 → Cloudflare Pages 자동 배포 → `https://nkstudio.org` 반영이다.
   - 푸시 성공 후 운영 사이트의 앱 버전과 변경된 빌드 산출물을 확인한다. 푸시 성공만으로 배포 완료를 보고하지 않는다.
7) 증빙 보고
   - Assistant 응답에 “브랜치/최신 커밋 해시/앱 버전/운영 배포 확인 결과/요약”을 포함한다.
8) 실패 대응
   - 테스트 실패는 원인을 해결한 뒤 재검증하고 릴리스를 재개한다.
   - 인증·배포·자동 승인 검토 등 실제 차단이 있으면 해결 가능한 조치를 진행하고, 남은 차단 원인을 정확히 보고한다. 로그인 등 사용자님의 직접 조작이 필요한 경우에만 해당 조작을 요청한다.

### 자동화(훅) 규정
- 로컬 훅 경로: `.githooks` (PowerShell `scripts/setup-hooks.ps1`로 설정)
- `pre-commit`
  - `npm test`를 실행해 실패 시 커밋 차단
  - `prototype/js/config.js` 버전이 변경되지 않았다면 자동으로 패치 버전을 +1 하고 스테이징
- `post-commit`
  - 커밋 성공 시 `origin/main`으로 자동 푸시
- `pre-push`
  - 푸시 직전 `node --test prototype/tests/*.test.mjs`로 테스트 실패 시 푸시 차단

### 실패 방지·재발 방지 가이드
- 훅 미작동 대비: 훅이 비활성화되어도 Assistant가 직접 “테스트→버전↑→커밋→푸시→운영 배포 확인”을 실행한다.
- 메시지 일관성: 커밋 메시지에 “앱 버전”을 명시해 추적성을 확보한다.
- 검증 우선: 테스트가 없다면 최소한 빌드·정적 검사(가능할 때)를 수행한다.
- 사용자 예외 준수: 사용자가 “푸시 금지”를 요청하면 해당 턴에서는 결과만 보고하고 푸시는 하지 않는다.
